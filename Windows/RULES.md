## 🔒 1. Сохранение функционала (Zero Regression Rule)
- **НИЧЕГО ИЗ СУЩЕСТВУЮЩЕЙ ФУНКЦИОНАЛЬНОСТИ УДАЛЯТЬ НЕЛЬЗЯ**, если пользователь (Владимир) конкретно и явно об этом не попросил.
- Все существующие элементы интерфейса, кнопки, логика, профили, диагностика, сетевые протоколы, горячие клавиши и контекстные меню должны строго сохраняться и оставаться полностью работоспособными при любых доработках.

## ⚡ 2. Новая версия при любом изменении (Auto-Bump Version)
- При **ЛЮБОМ** изменении, исправлении, добавлении или удалении функций **ВСЕГДА создается следующая рабочая версия** (например, `v023` -> `v024`, `v034` -> `v035`).
- Номер версии синхронно обновляется во всех файлах проекта:
  1. В константах кода (`AppVersion = "v024"`, `AppTitle = "...[v024]"`);
  2. В имени скомпилированного бинарника (`<AppName>_v024.exe`);
  3. В документации (`README.md`, `version.txt`);
  4. В реестре Windows и установщиках (`DisplayVersion`).

## 🖥️ 3. Обязательная доставка на Рабочий Стол через MEGA (MEGA Desktop Delivery)
- **Тотальное правило для всех Windows-установок (CMD, BAT, EXE):**
  - Во **всех проектах, скриптах и задачах, которые касаются установки программ, компонентов, утилит или развёртывания на ОС Windows**:
  - **ВСЕ создаваемые CMD-файлы, BAT-скрипты, PowerShell-лаунчеры и скомпилированные EXE-файлы/установщики ИИ ОБЯЗАН АВТОМАТИЧЕСКИ копировать на настоящий Рабочий стол Владимира в папку облака MEGA строго по пути:**
    `D:\MEGA\DOCS\desktop\` (или через команду `mega-put -c "<file>" "/MEGA/DOCS/desktop/"` на удалённых серверах).
  - Запрещено ограничиваться сохранением только во временных папках, папках проектов или `D:\DownLOAD\` — на Рабочем столе в `D:\MEGA\DOCS\desktop\` всегда должна быть готова к запуску актуальная копия каждого созданного установочного файла.
- Сразу после сборки нового бинарника или создания установочного CMD/BAT/EXE файла агент **НЕМЕДЛЕННО И АВТОМАТИЧЕСКИ**:
  1. Удаляет старую версию с Рабочего стола в облаке MEGA:
     ```bash
     mega-rm "/MEGA/DOCS/desktop/<AppName>_v<OLD>.exe" 2>/dev/null || true
     ```
  2. Загружает/копирует новую скомпилированную версию или CMD/EXE установщик на Рабочий стол пользователя:
     ```bash
     mega-put -c "<path_to_binary>_v<NEW>.exe" "/MEGA/DOCS/desktop/"
     ```
     *(На локальном ПК под Windows выполняется прямое копирование в `D:\MEGA\DOCS\desktop\`)*.
  3. Загружает резервные копии в облачные каталоги утилит (`/MEGA/WIN-FLASH/Util-WINDOWS/...`).
- На Рабочем столе пользователя всегда должна быть **строго одна актуальная версия** каждого установщика или приложения.

## 📦 4. Стандарт Легковесных Онлайн-Установщиков (<AppName>_Installer.exe)
1. **Единый стандарт именования:**
   - Все компактные онлайн-установщики обязаны строго следовать формату: `<AppName>_Installer.exe` (например: `GIN-VPN_Installer.exe`, `GIN-NetScan_Installer.exe`).
   - Запрещено именование с префиксом действия типа `Install_<AppName>.exe`, чтобы файлы в проводнике Windows и каталогах облака MEGA автоматически группировались по алфавиту рядом с основным приложением.
2. **Характеристики и визуальный стиль:**
   - Нативный компактный C#/.NET исполняемый файл размером **до 50-70 КБ** (без внешних тяжелых фреймворков и библиотек, компиляция встроенным `csc.exe` .NET 4.0/4.8).
   - Обязательное внедрение фирменной иконки приложения (`/win32icon:<AppName>.ico`).
   - Автоматический запрос прав администратора (UAC elevation) при необходимости записи в `C:\Program Files`.
   - Графический интерфейс в темной стилистике с живым индикатором загрузки, процентами и отображением текущего сервера-зеркала.
3. **Динамическое определение версии и защита от устаревших зеркал (Anti-Stale):**
   - Установщик не имеет права слепо скачивать неверсионированный файл `.../<AppName>.exe` с первого доступного сервера без сверки версии.
   - Перед загрузкой установщик опрашивает `version.json` / `version.txt` (с антикэш-штампом `?t=<timestamp>`), определяя точную актуальную версию (например, `v079`) и официальный URL релиза.
   - Загрузка производится в первую очередь по версионированным ссылкам (`<AppName>_v<LATEST>.exe`).
   - После завершения скачивания временный файл проходит обязательную проверку содержимого на наличие сигнатуры целевой версии: если сторонний сервер вернул старый кэшированный бинарник, файл отбрасывается, а установщик переходит к следующему зеркалу (GitHub / CloudCore-191).
4. **Размещение в хранилище:**
   - Легковесный установщик хранится в облачном каталоге утилит `D:\MEGA\WIN-FLASH\Util-WINDOWS\...` вместо 20-мегабайтных монолитных дистрибутивов.

## 🌐 5. Синхронизация с GitHub (GitHub Project Release)
- Скомпилированный бинарник (`<AppName>_v<NEW>.exe` и `<AppName>.exe`), установщик `<AppName>_Installer.exe`, исходный код и `README.md` немедленно фиксируются коммитом и пушатся в репозитории проекта:
  - [Windows_scripts ↗](https://github.com/GinCz/Windows_scripts) — `Windows/<AppName>/`
  - [Linux_Server_Public ↗](https://github.com/GinCz/Linux_Server_Public) — `Windows/<AppName>/`
  - [Secret_Privat ↗](https://github.com/GinCz/Secret_Privat) — `Windows/<AppName>/`
- Старые бинарники удаляются из репозиториев (`git rm <old_binary>.exe`), чтобы не раздувать размер Git.

## 🔗 6. Железное Правило Кликабельных Ссылок и Репозиториев (Clickable Links & Repos Mandate)
1. **Строго кликабельные markdown-ссылки со стрелочкой `↗`:**
   - Все ссылки, передаваемые пользователю (Владимиру) в сообщениях, ОБЯЗАНЫ быть кликабельными ссылками на GitHub со стрелочкой `↗` на конце (например: `[Windows_scripts ↗](https://github.com/GinCz/Windows_scripts)`).
   - Категорически запрещено отправлять локальные файловые ссылки (`file:///...`) или некликабельный плоский текст путей.
2. **Обязательная кликабельная ссылка на репозиторий при любых коммитах:**
   - При внесении любых изменений (commit, push) в проект `Windows_scripts` или связанные репозитории, агент **ОБЯЗАН в тексте своего ответа предоставить прямую кликабельную ссылку на конкретно этот репозиторий на GitHub**.
